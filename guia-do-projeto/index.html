O problema e o produto

Resumo de 30 segundos

  • O Kolô é um ateliê de arte e estúdio de tatuagem que perdeu o espaço físico em Pinheiros. Hoje vende, agenda e controla tudo à mão, por conversa.

Arquitetura: monolito modular

Resumo de 30 segundos

  • Uma aplicação só (Next.js) faz as telas e o servidor, em TypeScript. Um banco (PostgreSQL). Tudo em contêineres Docker numa VPS.
  • “Modular” quer dizer que o código é dividido por domínio em src/modules/, e um módulo só usa outro pela porta da frente (index.ts).
  • Serviços externos: Mercado Pago (pagamento), Cloudflare R2 (imagens), Resend (e-mail), Turnstile (antibot) e links do WhatsApp.

As três formas de o servidor responder no Next.js

Server Components

A página é montada no servidor, já com os dados do banco. O navegador recebe HTML pronto e menos JavaScript. Ex.: catálogo, ficha da obra, painel do admin.

Server Actions

Funções do servidor chamadas direto por um formulário, sem escrever uma API REST. Ex.: src/app/admin/actions.ts, finalizar compra, salvar horário.

Route Handlers

Endpoints HTTP de verdade, para quem está fora do site. Ex.: src/app/api/webhooks/mercadopago/route.ts, que o Mercado Pago chama.

Mapa dos módulos (src/modules/)

Cada pasta é um domínio. A regra é: quem está fora de um módulo só importa o index.ts dele. Assim dá para mudar o interior de um módulo sem quebrar os outros. A única exceção é o cliente.ts, com código puro que pode ir para o navegador quando o index.ts puxa coisa de servidor (SDK, sharp, banco).

O núcleo da compra

A regra mais elegante: agenda sem sobreposição no próprio banco

Um artista não pode ter dois horários que se encostam no tempo (RN08). Em vez de confiar só no código, a migração cria uma restrição de exclusão: o Postgres recusa qualquer linha cujo intervalo se cruze com outro do mesmo artista. Funciona mesmo se duas pessoas salvarem ao mesmo tempo.

-- prisma/migrations/0001_init/migration.sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "appointment"
  ADD CONSTRAINT "appointment_no_overlap"
  EXCLUDE USING gist (
    "artist_id" WITH =,                                  -- mesmo artista
    tstzrange("inicia_em", "termina_em", '[)') WITH &&   -- intervalos que se cruzam
  )
  WHERE ("excluido_em" IS NULL AND "situacao" <> 'CANCELADO');

Feature: loja e pagamento

Resumo de 30 segundos

  • Quando o cliente vai pagar, a obra fica reservada por 10 minutos para ele. Duas pessoas nunca compram a mesma peça única.
  • O pedido só vira PAGO quando o Mercado Pago avisa pelo webhook assinado, e mesmo assim nós consultamos a API para confirmar.
  • Se o mesmo aviso chegar duas vezes, ele é processado uma vez só (idempotência).

Por que duas pessoas nunca levam a mesma obra

Imagine a última unidade de uma tela e dois clientes clicando em “finalizar” no mesmo segundo. Sem cuidado, os dois leriam “estoque = 1” e os dois comprariam. Feature: agendamento e portfólio

Resumo de 30 segundos

  • O wizard faz 8 perguntas, uma por tela, e abre o WhatsApp do estúdio com a mensagem pronta. Não grava nada.
  • Três avisos obrigatórios (anamnese, termo e maioridade) só liberam o botão. Eles não viram dado no banco.
  • Depois de combinar na conversa, o artista ou o admin cadastra o horário, e o banco impede sobreposição.

    Do wizard ao horário na agenda

    Visitante preenche o wizard→ Abre o WhatsApp com a mensagem→ Conversa: referências, valor, data→ Artista/admin cadastra o horário (RF22)→ Banco recusa se sobrepuser (RN08)

    A agenda mostra a semana do artista. O artista só vê e edita a própria agenda e o próprio portfólio (RN10); o admin vê todos. Os próximos 7 dias aparecem também no painel do admin.

    Portfólio de tatuagens

    Galeria pública filtrável por artista, estilo e região do corpo, com busca por palavra-chave (RF17, RF18). O admin e o próprio artista incluem, editam, ordenam, destacam e removem fotos (RF19). As imagens sobem para o R2 com URL assinada e passam pelo sharp, que confirma que o arquivo é mesmo uma imagem e gera a miniatura.

    Como a permissão é conferida

    Toda operação do admin passa por comoAdmin. Ele lê a sessão do cookie, confere o papel e, dentro de uma transação serializável, busca a sessão de novo no banco e confere se o usuário ainda é ADMIN, está ativo e não foi excluído. Se alguém for rebaixado ou tiver a sessão revogada, perde o acesso na hora, sem esperar um token vencer.

    // src/modules/artists/acesso.ts (resumo)
export async function comoAdmin(cabecalhos, executar) {
  const sessao = await sessaoDaRequisicao(cabecalhos);   // sem sessão → "nao_autenticado"
  if (sessao.papel !== "ADMIN") throw ...;            // → "proibido"
  return prisma.$transaction(async (tx) => {
    // relê no banco: sessão válida, papel ADMIN, ATIVO, não excluído
    return executar(tx);
  }, { isolationLevel: "Serializable" });
}

    Segurança e LGPD

    Resumo de 30 segundos

    • O sistema evita guardar o que é perigoso: nenhum dado de cartão e nenhum dado de saúde.
    • Toda entrada é validada no servidor (Zod), todo SQL é parametrizado (Prisma) e o React escapa o HTML.
    • HTTPS e cabeçalhos de segurança dependem do deploy, que ainda está pendente.
    Ameaça ou exigênciaComo tratamosSituação
    Senha vazada do banco (RNF03)Só o hash, com algoritmo lento e salt por usuário (Better Auth). Token de recuperação também só como hash.feito
    SQL Injection (RNF04)Prisma parametriza tudo; onde usamos SQL direto, é $queryRaw com template (os valores viram parâmetros) ou pool.query com $1.feito
    XSS (RNF05)O React escapa o texto. Upload não aceita SVG (poderia carregar script). CSP restritiva fica com o deploy.escape CSP
    CSRF (RNF06)Server Actions conferem a origem da requisição; cookies de sessão HttpOnly e SameSite.feito
    Força bruta e spam (RNF08)Tabela rate_limit no Postgres; o contador soma e decide num só comando (INSERT … ON CONFLICT), então uma rajada simultânea não escapa. A chave é um hash de IP + e-mail. Turnstile no contato.feito
    Entrada maliciosa (RNF09)Esquemas Zod em validacao.ts de cada módulo, sempre no servidor.feito
    Dado de cartão (RNF10)O cartão é digitado no Checkout Pro do Mercado Pago. Nunca passa pelo Kolô.feito
    Webhook falso ou repetido (RNF11)Assinatura HMAC conferida pelo validador oficial do SDK; evento com id único.feito
    Segredo no Git (RNF12)Tudo em variável de ambiente; .env fora do versionamento; o servidor confere as variáveis de produção ao subir.feito
    HTTPS e cabeçalhos (RNF01, RNF07)Caddy com certificado automático, HSTS, X-Frame-Options etc.deploy
    Dado de saúde (RNF18)Não existe tabela nem campo para isso. Os checks do wizard não são gravados.feito
    Direito de sair (RNF19, RN12)O cliente exclui a conta; os dados pessoais são anonimizados e os pedidos pagos ficam.feito
    💡

    Frase para guardar: “O dado mais seguro é o que a gente não guarda.” Ela resume três decisões: cartão no Mercado Pago, saúde presencial e o wizard sem persistência.

    Como o grupo trabalha

    O processo está escrito em AGENTS.md e vale para pessoas e para os assistentes de IA usados no desenvolvimento:

    1. Pedido em 4 blocos antes de codar: o que quero, como, o que não quero, como sei que está pronto (comando + saída).
    2. TDD em fatias verticais: um teste que falha, o mínimo de código para passar, repete. Nada de escrever todos os testes primeiro.
    3. “Pronto” é comando executado: npm run lint, npm run typecheck e npm test com a saída à vista.
    4. Revisão por outra pessoa ou agente no fim da feature: quem escreveu não é quem aprova.
    5. Commits pequenos, um PBI por vez, no padrão Conventional Commits.

    Checklist “sei explicar”

    Marque só o que você consegue explicar sem olhar. As marcações ficam salvas neste navegador.

      Glossário

      RF / RNF / RN
      Requisito funcional (o que o sistema faz), não funcional (como ele deve ser: seguro, rápido, acessível) e regra de negócio (política do Kolô que o sistema impõe).
      P0 / P1
      Prioridade: P0 é indispensável para a defesa; P1 entra se o P0 fechar.
      PBI
      Item do backlog do produto. Cada feature tem um, em docs/features/ e nos documentos de sprint.
      Monolito modular
      Uma aplicação e um deploy só, com o código dividido em módulos de fronteira clara.
      Server Action
      Função do servidor que o formulário chama direto, sem escrever uma API.
      Route Handler
      Endpoint HTTP do Next.js. O webhook do Mercado Pago é um.
      Transação
      Grupo de operações no banco que acontece inteiro ou não acontece.
      FOR UPDATE
      Tranca as linhas lidas até a transação terminar, para outra transação esperar em vez de ler um valor velho.
      Restrição de exclusão
      EXCLUDE USING gist: o Postgres recusa duas linhas que “colidem”, como dois horários sobrepostos do mesmo artista.
      Webhook
      Aviso que outro sistema manda para o nosso quando algo acontece (ex.: pagamento aprovado).
      HMAC
      Assinatura feita com um segredo compartilhado. Prova que o aviso veio do Mercado Pago e não foi alterado.
      Idempotência
      Processar a mesma coisa duas vezes dá o mesmo resultado que processar uma vez.
      Preferência
      A “cobrança” criada no Mercado Pago, com itens e URLs. Gera o link do checkout.
      Sandbox
      Ambiente de teste do Mercado Pago: pagamentos de mentira, mesmo código de produção.
      URL assinada
      Link temporário que autoriza um envio ao R2 sem expor as credenciais.
      Seed
      Script que coloca dados iniciais no banco (prisma/seed.ts).
      Migração
      Arquivo SQL versionado que muda a estrutura do banco, em ordem.
      LCP
      Largest Contentful Paint: tempo até o maior elemento da tela aparecer. Meta abaixo de 2,5 s.
      E2E
      Teste ponta a ponta: um navegador de verdade clicando no sistema rodando.
      TDD
      Escrever o teste antes do código: vermelho, verde, repete.
      Anonimizar
      Trocar os dados pessoais por valores que não identificam ninguém, mantendo o registro.
